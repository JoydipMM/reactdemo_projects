These features help improve SEO, reduce client-side JavaScript, speed up page loads, and simplify application architecture. In production applications such as e-commerce platforms, SaaS products, OTT platforms, and content websites, Next.js allows us to build scalable, high-performance applications with a better developer experience than plain React.

  • Server Component
  • Server Actions
  • Built-in Routing

  • caching
  • Full-Stack Capabilities
  • Performance Optimizations: Image optimization, Streaming, Lazy Loading, Route-level caching, Partial Prerendering

What is Routing?

Routing is the mechanism that maps a URL to a specific page, component, or resource in an application. When a user visits a URL, the routing system determines which page should be rendered.


How Routing Works in Next.js

Next.js uses File-Based Routing. Next.js automatically creates routes from folders and files inside the app directory.

7. Parallel Routes

parallel routes allow you to simultaneously or conditionally render one or multiple pages at the same level with in the same layout. They are useful for scenarios where you want to display different content or components based on user interactions or specific conditions without navigating away from the current page. With parallel routes, you can have multiple routes active at the same time, allowing for a more dynamic and responsive user experience.

parallal routes are created using name slots. Slots are defined with @folder convention.

Slots are passed as props to the shared parent layout.

When we go to sales page then it will show sales page and url will be localhost:3000/dashboard/sales

If we click on back link then it will show Dashboard Page and url will be localhost:3000/dashboard


Important Note:


We will get error if we go to localhost:3000/dashboard/sales by click on Go to Sales link when we are on Dashboard Page and after goto localhost:3000/dashboard/sales page and refresh the full page, then we will get error like: GET http://localhost:3000/dashboard/sales 404 (Not Found) in Console and redirect to 404 page


Reason for error

  • When we performing a full page refresh, nextjs to lose the current state of slots.

  • Navigating to a route that doesn't have a corresponding page in a slot.


Error explain in detail:

When we navigate using , Next.js performs a soft navigation and remembers the active state of the parallel routes. However, when we refresh: /dashboard/sales Next.js performs a hard navigation. At that moment, Next.js knows: sales = active but it doesn't know what should be rendered inside: @analytics because that slot isn't part of the URL. Without a fallback, Next.js cannot recover the state of the unmatched slot and may render a 404.

*** Fallback simply means: Next.js renders when it cannot find or restore the correct content for a route segment. Think of it as a default replacement. ***.

Real-Life Example: Suppose we have a dashboard: /dashboard with two parallal routes @sales, @analytics. When we visit: /dashboard/sales Next.js knows: @sales → render sales page But after a page refresh, it doesn't know what to render in: @analytics. because the URL doesn't contain any information about the analytics slot. Without a fallback:

Result: GET http://localhost:3000/dashboard/sales 404 (Not Found)

Solution:

To handle the unmatch routes gracefully, nextjs introduces the default.jsx/tsx file with in each slots. This file serves as a fallback UI when,

  1. A slot doesn't have a matching route for the current URL.

  2. When the user performs a full page refresh and nextjs to lose the current state of a slot.


With default.tsx (Fallback): Next.js knows: @sales → render sales page and @analytics → render default page

Now after refresh:

Next.js uses default.tsx as the fallback UI.


Interview Answer

In Parallel Routes, a page refresh or direct URL access causes a hard navigation. Next.js can only determine the active slot from the URL and cannot restore the state of unmatched slots. If those unmatched slots don't provide a default.tsx, Next.js may render a 404. Therefore, in production applications we add default.tsx to parallel route slots to provide fallback content and allow the application to recover correctly during hard navigations and page refreshes.

useRouter Hook

useRouter is a hook allow us to programmatically change routes inside client component

Method of useRouter:

  1. router.push() method navigates to a new route and adds it to the browser history stack. So if we navigate back using the browser's back button, the previous route will be restored.
    Example:

    Suppose we are in http://localhost:3000/userouter page. Now if we click on "UseRouter push router-01" button, it will navigate to http://localhost:3000/userouter/router-01. Click on "UseRouter push router-02" button, it will navigate to http://localhost:3000/userouter/router-02. Same way we can navigate to "Userouter push router-03". Now if we click on browser back button, it will navigate to router-02 > router-01 > userouter.
  2. router.replace() method navigates to a new route but does not add it to the browser history stack.
    Example:

    Same here also we are in http://localhost:3000/userouter page. Now if we click on "UseRouter push router-01" button, it will navigate to http://localhost:3000/userouter/router-01. Click on "UseRouter push router-02" button, it will navigate to http://localhost:3000/userouter/router-02. But now if we click on "UseRouter replace router-03", it will navigate to http://localhost:3000/userouter/router-03. Now if we click on browser back button, it will navigate to router-01.
  3. router.refresh() method re-fetches the server data and re-renders the current page without reloading the entire page.
  4. router.back() method navigates to the previous route in the browser history stack.
  5. router.forward() method navigates to the next route in the browser history stack.

The browser can store the cookies and send them back to the same server with the future requests.

Server Actions

server actions are asynchronous function that run only on the server and can be called directly from the react component

they allow to execute server-side logic such as database operations, authentication and handling without creating API routes

In general if we want to call any API in Nextjs component then first we use fetch/axios request to create web request then it goes to API routes and API route talks to database. So we need create a backend endpoint manually.

But when it comes to "Server Actions", component can be client/server we write a asynchronous function and that asynchronous function can directly talk to database and perform some server side logic. So we no need to manage any request / response handling manually. Means Server Actions remove internal API Routes.


When to use server actions
  • They simplify mutations like: create, update, delete oparations
  • Nestjs suggest us don't use "Server Actions" to fetch API. But we can use this for create, edit delete actions.

A server Action is a server-side function marked with "use server" directive that can be invoked from React components.

This "Server Action" directive tell Nextjs to treat the function as a server action

Directive can be use at the Top of the file / inside in specific asynchronous function

If we want use a file as a server action then we need to add "use server" directive at the top of the file like action.js/ts.

So, when "use server" is placed at the top of the file, Nextjs treats the file as a server action and all export function are run on the server

Example: Most comonly used in form

Next.js Form Component

The Form component in Next.js is an enhanced version of the HTML form element that integrates tightly with the App Router, Server Actions, and client navigation.

Instead of manually handling form submission with JavaScript, Next.js lets you directly connect a form to server functions or routes.


Why Next.js introduced Form component

In traditional React or Next.js apps, forms required:

  • onSubmit handlers
  • fetch() calls
  • API routes
  • manual navigation

How Form componentworks

The behavior of Form component depends on the type of action prop:

  1. When action is a string: action="/search" then it's behavior:
    • work like normal HTML form
    • Uses GET request
    • Converts from inputs to URL search params
    • Performs "client-side navigation"

    Converts from inputs to URL search params > when user submit the form then form data convert to url params like: /search?title=raja&age=40

  2. When action is a function (Server Action): action={createPostAction} then it's behavior:
    • Calls a Server Action
    • Sends data via POST
    • No API router required
    • Function receives "FormData" automatically. example: async function createPostAction(){...}

Benefits of using Form component
  1. Less Boilerplate No need for:
    • API routes
    • Fetch requests
    • manual event handling
  2. Direct Server Communication Forms can call "Server Actions" directly, reducing architecture complexity.
  3. Client-Side Navigation No full reload.
    benefits:
    • faster User experience
    • preserved state
    • layouts stay mounted
  4. URL Search Param Integration
    great for:
    • search bars
    • filters
    • pagination

TanStack Query

TanStack Query (formerly known as React Query) is an asynchronous server state management library designed for fetching, caching, synchronizing, and updating server state in web applications. It eliminates the need for manual data fetching logic using complex useEffect chains and multiple useState hooks.


The Problem It solves:

When fetching data in React or Next.js manually, developers usually write code like:

  • fetch() inside useEffect
  • manage loading
  • manage error
  • store data in useState
  • handle refetching

Why we use TanStack Query in Next.js

TanStack Query helps when application need:

  • Server-side API fetching
  • Infinite Scroll
  • Pagination
  • Frequently updated data

Instead of writing repetitive fetching logic, we use query hooks like useQuery().


QueryClientProvider

To make TanStack Query available across the app, we wrap the application with QueryClientProvider. This provider gives all components access to the query client and cache system


Core TanStack Query terms:
  • Query - A request to the server for fetch data, to use query hooks useQuery
  • Mutation - Change the data on the server like: POST, PUT, PATCH, DELETE. For mutation hooks useMutation
  • cache - A cache system for storing and retrieving the fetched data. So same request will not be sent to the server again if the data is already in the cache atleast for a certain period of time with the help of queryKey
  • QueryKey - A unique identifier for a query in the cache
  • QueryFunction - A function that fetches data
  • Stale Data - Data that is not up to date. TanStack Query consider cache data is a stale by default. When ever we worked with cache data then TanStack Query consider that it is not up to date. To update the cache data we need to use refetch
  • Refetching - Fetching data from the server again
  • Invalidation - update the cache data as stale so that it can be refetched, Means I wanted to fetched the latest data.
  • QueryClient - QueryClient manages the cache and all queries.

useQuery in TanStack Query - Simplifies Data Fetching

Fetching data in React traditionally requires multiple steps and a lot of boilerplate code. TanStack Query introduces the useQuery hook to simplify this process and handle many tasks automatically.

useQuery makes data fetching declarative, cleaner and easier to maintain by removing most of the manual state management and boilerplate code.

useMutation in TanStack Query

useMutation is a hook that handles server-side changes (mutations) and provides build-in tools to manage loading state, errors and side effects.

useMutation handles server-side updates, invalidateQueries refreshes outdated data, and optimistic updates make the UI feel instant and responsive.


Query Invalidation
After a mutation changes data on the server, cached queries may become outdated. To fix this, we invalidate the query, which marks it as stale and triggers a refetch.
Optimistic UI

Normally the UI waits for the server response before updating.

Example: Click Like -> request -> wait -> UI updates

This can feel slow.

Optimistic UI updates the interface immediately, assuming the request will succeed. If the request fails, the UI rolls back.
