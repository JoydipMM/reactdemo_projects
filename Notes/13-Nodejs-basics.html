Node.js Basic

Node.js is a JavaScript runtime environment that allows you to run JavaScript code outside of a web browser, most commonly on servers. Node.js provides an environment where JavaScript can run directly on your computer or a server. It is built on the Chrome V8 JavaScript engine and is widely used for building web servers, APIs, real-time applications, and command-line tools.


Why is Node.js single-threaded?

Node.js is called single-threaded because JavaScript executes on a single main thread managed by the event loop. Instead of creating a new thread for every request, it uses asynchronous, non-blocking I/O to handle many concurrent operations efficiently. Slow tasks like file access and cryptography are offloaded to libuv's worker thread pool or the operating system. This design minimizes thread overhead and makes Node.js highly scalable for I/O-bound applications, while CPU-intensive tasks can be handled using worker threads or separate processes.


What is Non-Blocking I/O?

Non-blocking I/O means that Node.js does not wait for an input/output operation (file, database, network, API, etc.) to finish before executing the next line of code.

path.resolve()

path.resolve() is a method of Node.js's built-in path module. It converts a sequence of path segments into an absolute path.

Syntax

  • Accepts zero or more path segments.
  • Processes the paths from right to left.
  • Stops when it encounters an absolute path.
  • If no absolute path is found, it uses the current working directory (process.cwd()).

Importing the Path Module


When should you use path.resolve()?

Use path.resolve() when you need an absolute path, such as when:

  • Reading or writing files with the fs module.
  • Configuring file uploads.
  • Serving static assets in web servers.
  • Building reliable paths that don't depend on where a script is called from.

Summary

  • path.resolve() always returns an absolute path.
  • It resolves . (current directory) and .. (parent directory).
  • It processes path segments from right to left and stops when it finds an absolute path.
  • If no absolute path is provided, it starts from the current working directory (process.cwd()).

Event Emitter

EventEmitter is a built-in class in Node.js that allows objects to emit (trigger) events and listen for those events. It is the foundation of Node.js's event-driven architecture.

  • Emitter → Announces that something happened.
  • Listener → Waits for that event and responds to it.

Why do we need EventEmitter?

Without EventEmitter everything is tightly coupled. Take the below taskCompleted() function as an example. Here we have 3 functions that are tightly coupled. So when taskCompleted() is called, all 3 functions are called. There is no way to call indivitual functions separately. So to solve this problem we use EventEmitter, which allows us to call individual functions separately with independent listeners

What is origin?

origin is automatically sent by the browser in the HTTP request. Suppose our API is http://localhost:5000. If your React app runs on http://localhost:3000, then origin will be http://localhost:3000.

Why !origin?

Some requests don't have an Origin header. like Postman, curl, server-to-server requests, some mobile apps, same-origin requests in certain situations. In those cases, origin will be undefined, then !origin will return true. So we can say that "If no Origin header exists, allow the request."

What is allowedOrigins?

This is simply a whitelist. Only these websites can access your API.

At present only these websites can access our API and only these three origins are allowed.

What does allowedOrigins.indexOf(origin) do?

allowedOrigins is an array of whitelisted URLs (origins) that are permitted to access the API through CORS.

indexOf(origin) searches the allowedOrigins whitelist array for the origin received from the browser and returns its index if found; otherwise, it returns -1

  • Senario 1

    Here allowedOrigins.indexOf(origin) will return 0. because it is found at index 0.

  • Senario 2

    Suppose our origin is "https://google.com"

    But our allowedOrigins is ["http://localhost:3000"]. So it will return -1, because it doesn't exist.

Why use OR (||)?

The condition is !origin || allowedOrigins.indexOf(origin) !== -1 It means allow the request if either:

  • there is no Origin header, OR

  • the Origin is present in the whitelist.

!== -1 means The value is not equal to -1

Some Senarios:

  • Scenario 1 (React App): origin is http://localhost:3000

    !origin means No Origin header exists then it return true

    But here we get origin from React App http://localhost:3000.

    That means origin exists. Then ***!origin will return false

    allowedOrigins = ["http://localhost:3000"] means that in allowedOrigins array list at index of 0 http://localhost:3000 url found and React app can access our API

    allowedOrigins.indexOf(origin) will return 0

    So, 0 !== -1 will return true because 0 is not equal to -1

  • Scenario 2 (Postman): Origin: undefined

    Then !origin will return true

    So, when it get true from !origin, it will return callback(null, true). That means Allow the request and it will not check allowedOrigins.indexOf(origin)

  • Scenario 3 (Unknown Website): Origin: http://unknownwebsite.com

    Here !origin will return false

    So, when it get false from !origin, it will check allowedOrigins.indexOf(origin). Here also allowedOrigins.indexOf(origin) will return -1. So -1 !== -1 will return false. That means Deny the request

    0 !== -1 means 0 is not equal to -1 so this is true

    -1 !== -1 means -1 is not equal to -1 so this is false

Pub/Sub in Redis

Pub/Sub (Publish/Subscribe) is a messaging pattern where Publisher → Sends messages, Subscriber → Receives messages, Channel → The medium through which messages travel

The publisher doesn't know who the subscribers are. The subscribers don't know who published the message. They only communicate through a channel.

Real-life Example: Imagine a YouTube channel.

  • We upload a new video → Publisher
  • subscribers receive notification → Subscribers
  • YouTube channel → Channel

We don't send notifications individually. You just upload. Everyone subscribed receives it. Redis Pub/Sub works exactly like this.

Code Breakdown

  • const logger = winston.createLogger(); - creates a new logger instance
    This logger object provides methods like:

  • Code Structure
  • 1. Logging Level

    This determines which log levels should actually be written.

    if NODE_ENV=production then level = "info", then Winston logs only "error", "warn", and "info" messages. and
    if NODE_ENV=development then level = "debug", then Winston logs all messages ( "error", "warn", and "info" ).

  • 2. Format

    winston.format.timestamp() Automatically adds the current time.
    Without timestamp: { "level":"info", "message":"User logged in" }
    With timestamp: { "level":"info", "message":"User logged in", "timestamp":"2023-05-15T07:42:08.000Z" }
    This helps to identify when an event happened.

    winston.format.errors({ stack: true }) adds the stack trace to the log message if there is an error.
    Normally, we use logger.error(new Error("Database Error")); might produce without stack trace. : { "message":"Database Error"}
    with stack: true it becomes { "message":"Database Error", "stack":"Error: Database Error\n at ..." }
    The stack trace shows where the error occurred, making debugging much easier.

    winston.format.splat() This enables printf-style placeholders.
    Example: logger.info("User %s logged in", "John");
    Without splat: User %s logged in
    With splat: User John logged in

    winston.format.json() Converts the log into JSON.
    Instead of info: User logged in
    we got: { "timestamp":"2026-08-06T10:22:00Z", "level":"info", "message":"User logged in" }

  • 3. Default Metadata:

    Adds the same metadata to every log.

    Adds the same metadata to every log.
    Example: logger.info("User created");
    output: { "service":"auth-service", "message":"User created" }
    Why need default metadata?
    Imagine we have multiple services: auth-service, user-service, and product-service.
    When all logs are collected in one place, we can quickly filter logs from the auth-service.

  • 4. Transports

    A transport defines where the logs are written. One log message can be sent to multiple destinations.

  • 5. Console Transport

    Logs are printed to the terminal.

    winston.format.colorize() Makes log levels easier to distinguish. Example: INFO (green) WARN (yellow) ERROR (red)
    winston.format.simple() Outputs concise, human-readable logs. Example: info: User logged in

  • 6. new winston.transports.File({ filename: 'logs/error.log', level: 'error' }),

    Log errors to a file.

  • 7. new winston.transports.File({ filename: 'logs/combined.log' })

    Log all messages to a combined log file.
